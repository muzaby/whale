# Whale PRD (Product Requirements Document)

- 문서 버전: v0.1
- 작성일: 2026-04-28
- 범위: Whale 웹 기반 이미지 ISP 튜닝 도구 (Home / E2E / Library)

---

## 1. 기획 배경
Whale은 카메라/이미지 신호처리 엔지니어가 레퍼런스 이미지와 시뮬레이션 결과를 비교하며 ISP 파이프라인 파라미터를 튜닝하는 도구다. 현재는 목업 단계이며, 화면 구조와 워크플로우가 이미 검증되어 있어 이를 실서비스로 전환해야 한다.

### 배경 근거
- 본 프로젝트는 디자인 핸드오프 번들로 제공되었고, 채팅/목업을 기준으로 실제 구현을 진행해야 한다.
- 핵심 기능 축은 `E2E`(파이프라인 튜닝)와 `Library`(이미지 자산 관리)이며 `Home`은 최근 작업/진입 허브 역할을 한다.

---

## 2. 문제 정의
현재 ISP 튜닝 업무는 다음과 같은 비효율이 존재한다.
- 파라미터 변경 이력과 결과 이미지 연결(라인리지) 관리가 어렵다.
- 레퍼런스 대비 결과 비교가 비표준화되어 반복 검증 비용이 높다.
- 실험 자산(업로드/시뮬) 검색/분류/재사용이 어렵다.

Whale은 이를 단일 워크스페이스에서 해결해야 한다.

---

## 3. 제품 목표
1. **비교 중심 튜닝 경험 제공:** split/slider/overlay 비교를 통해 빠른 품질 판단
2. **파이프라인 기반 실험 관리:** 노드/리스트/타임라인 뷰로 단계별 튜닝
3. **자산 재사용성 강화:** Library에서 ref/sim, 태그, 컬렉션 기반 탐색
4. **협업 가능한 이력 관리 기반:** 세션/리비전/출력 결과 연결

### 비목표(초기)
- 소비자용 사진 편집 앱 기능(스티커, 템플릿 등)
- 모바일 앱 우선 최적화
- 범용 DAM 전체 기능(고급 워크플로우 자동화 등)

---

## 4. 대상 사용자 및 페르소나

### Primary User
- 이미지 신호처리 엔지니어
- 카메라 튜닝 엔지니어

### 페르소나 A: ISP Tuning Engineer
- 목표: 저조도/역광/혼합광 등 조건에서 파이프라인 성능 최적화
- Pain point: 반복 실험 시 비교/기록/재현성 부족

### 페르소나 B: Review Engineer
- 목표: 리비전 간 품질 차이 검토 및 승인
- Pain point: 결과물 출처(어떤 파라미터로 생성되었는지) 추적 어려움

---

## 5. 핵심 사용자 시나리오

1) 사용자는 Home에서 최근 세션을 열고 E2E로 진입한다.
2) E2E에서 파이프라인 블록을 선택해 Curves/HSL/Color Wheel/LUT를 조정한다.
3) Compare 뷰(Split/Slider)에서 ref/sim 차이를 확인한다.
4) Render 결과를 저장하고 리비전으로 남긴다.
5) Library에서 결과를 태그/세션/즐겨찾기로 정리하고 팀 리뷰에 활용한다.

---

## 6. 기능 요구사항 (MVP)

## 6.1 Home
- 최근 세션 리스트 제공
- 빠른 진입 액션(E2E 진입, Library 진입)
- 기본 작업 현황 지표(주간 작업량, 최근 활동)

## 6.2 E2E (핵심)
- 파이프라인 뷰 전환: Node / List / Timeline
- 비교 모드 전환: Split / Slider / Overlay(A-B blend)
- 블록별 튜닝 컨트롤
  - Tone Curves
  - HSL Slider
  - Color Wheels (Lift/Gamma/Gain)
  - White Balance
  - LUT 적용
  - Histogram (RGB/Luma)
- Render 요청 및 진행 상태 확인
- 리비전 저장/조회

## 6.3 Library
- 자산 표시 전환: Grid / List
- 자산 구분: Reference vs Simulation
- 검색/필터: 태그, 세션, 소스(ref/sim), 즐겨찾기
- 컬렉션/태그 기반 분류
- 메타데이터 노출(해상도/ISO/날짜/세션)

---

## 7. UX / 디자인 요구사항
- 전문가 도구 톤: DaVinci/Lightroom 계열의 고밀도 패널 구조
- 라이트 모드 기반 클린 UI
- 타이포: IBM Plex Sans + IBM Plex Mono
- 뷰/모드 전환은 즉시 반응해야 하며 주요 클릭 동작은 인터랙티브해야 함
- Tweaks 패널로 Accent/Density 변경 가능해야 함

---

## 8. 데이터 및 도메인 요구사항
- 주요 도메인 객체
  - Project, Session, Pipeline Revision, Asset, Job
- 필수 연결
  - Job은 입력 Asset + Pipeline Revision + 출력 Asset을 연결해야 함
- Asset 구분
  - source: `ref` / `sim`
- 추적성
  - 어떤 리비전이 어떤 결과를 만들었는지 lineage 조회 가능해야 함

---

## 9. 비기능 요구사항

## 9.1 성능
- E2E 화면 상호작용(모드 전환, 필터 전환)은 체감 지연 최소화
- 대용량 이미지 처리 요청은 비동기 Job 처리

## 9.2 신뢰성
- 실패 Job 재시도 및 실패 원인 확인 가능
- 장시간 작업에서도 상태 유실 없이 진행률 추적

## 9.3 보안
- 프로젝트 단위 RBAC
- 결과물 접근은 서명 URL 기반
- 변경 이력/렌더 실행 감사 로그

## 9.4 운영
- AWS 운영을 목표로 하며 개발/테스트는 LocalStack으로 재현 가능해야 함

---

## 10. 성공 지표 (초안)
- 튜닝 반복 시간 단축: 기존 대비 30% 이상
- 리비전 비교/재현 성공률: 95% 이상
- Render Job 성공률: 99% 이상
- Library 검색/필터를 통한 자산 재사용률: 월별 증가 추세

---

## 11. 릴리즈 범위

### MVP (1차)
- Home 기본 진입 허브
- E2E 핵심 튜닝 + 비교 모드 + Render Job 연동
- Library 업로드/검색/필터/구분(ref/sim)

### 2차 확장
- 협업 리뷰(코멘트/승인)
- 배치 렌더/우선순위 큐
- 고급 스코프(벡터스코프 등)

---

## 12. 의존성 및 리스크
- RAW 포맷 호환 범위 결정 필요
- ISP 엔진 연동 방식(내장 vs 외부 엔진) 결정 필요
- GPU 리소스 비용/확장 전략 필요
- 화질 평가 기준(KPI)의 객관화 필요

---

## 13. 오픈 이슈
- MVP에서 Overlay(A-B blend)를 포함할지 여부
- 초기 지원 카메라/센서 프로파일 범위
- 리뷰 승인 워크플로우의 최소 단위(세션/리비전)
- 업로드 파일 사이즈/포맷 제한 정책

---

## 14. 수용 기준 (Acceptance Criteria)
- [ ] 사용자 로그인 후 Home/E2E/Library 간 이동이 가능하다.
- [ ] E2E에서 Node/List/Timeline 전환이 동작한다.
- [ ] Compare 모드(Split/Slider)는 반드시 동작한다.
- [ ] 최소 1개 블록 파라미터 변경 후 Render Job 생성이 가능하다.
- [ ] 완료된 Job 결과가 Library에 `sim` 자산으로 저장/조회된다.
- [ ] Library에서 ref/sim 필터, 태그 필터, 즐겨찾기 필터가 동작한다.
- [ ] 리비전-결과 이미지 lineage를 조회할 수 있다.
