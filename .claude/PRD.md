## 1. Executive Summary

Whale은 이미지 신호처리 / 카메라 튜닝 엔지니어를 대상으로 한 **웹 기반 이미지 튜닝 스튜디오**다. 레퍼런스 이미지와 시뮬레이션 출력을 직접 비교하면서, 처리 파이프라인의 각 단계(블록)를 시각적으로 탐색하고 파라미터를 실시간으로 조정할 수 있다. DaVinci Resolve · Lightroom 같은 전문가 툴의 시각 언어를 차용하되, 카메라 튜닝 워크플로우(레퍼런스 ↔ 시뮬레이션 비교 + 파이프라인 블록 단위 조정)에 특화되어 있다.

**현재 단계**: HTML 프로토타입에서 React + TypeScript + Vite 코드베이스로 이식이 완료된 상태이며, **UI 골격과 주요 인터랙션은 동작하지만 실제 이미지 처리 / 파이프라인 실행 / 데이터 영속화는 미구현**이다.

## 2. Vision & Positioning

### 2.1 비전

> **"엔지니어가 이미지 튜닝의 결과를 즉시 보고, 파이프라인의 어느 단계에서 무엇이 어떻게 변하는지 직관적으로 추적할 수 있는 작업대를 만든다."**

### 2.2 포지셔닝

| 측면 | 정의 |
|------|------|
| **무엇이다** | 카메라/ISP 튜닝을 위한 비교 + 파이프라인 + 컬러 그레이딩 통합 워크벤치 |
| **무엇이 아니다** | 일반 사진 보정 도구 (Lightroom 대체), 영상 색보정 도구 (DaVinci 대체), 이미지 호스팅 서비스 |
| **차별점** | (1) ref/sim 비교가 1급 시민 (2) 파이프라인을 Node/List/Timeline 3가지 시점으로 동시 탐색 (3) 엔지니어가 익숙한 수치 메타데이터(monospace, tabular nums) 강조 |

### 2.3 디자인 원칙 *(원본 브리프 기반)*

1. **Light mode, professional tool aesthetic** — 따뜻한 오프화이트 배경(oklch 96~98%), 다크 네이비블랙 본문, 얇은 보더와 미세한 그림자
2. **Numerical clarity** — IBM Plex Mono로 수치/메타데이터 표기, tabular numerals로 정렬
3. **High density** — DaVinci/Lightroom처럼 좌우 패널 + 중앙 캔버스 구조, 화면 밀도 우선
4. **Single accent, multiple options** — 기본 액센트는 Ocean Blue, Tweaks를 통해 Teal / Amber / Graphite 4가지 선택
5. **View flexibility** — 동일한 데이터를 여러 시점으로 볼 수 있는 뷰 토글 (Pipeline 3종 / Compare 3종 / Library 2종)

## 3. Target Users

### 3.1 Primary Persona — *카메라 튜닝 엔지니어*

| 속성 | 내용 |
|------|------|
| **직군** | 카메라 모듈 / ISP / Image Quality 엔지니어 |
| **숙련도** | DaVinci, Lightroom, Photoshop 등 전문가 툴 경험 보유 |
| **주요 워크플로우** | (1) 센서/렌즈 모듈에서 레퍼런스 캡처 → (2) 시뮬레이션 파이프라인 실행 → (3) 결과를 ref와 비교 → (4) 색상/톤/디테일 파라미터 조정 → (5) 리비전 저장 |
| **핵심 니즈** | 차이를 빠르게 보고, 어느 블록 때문에 차이가 발생하는지 추적, 미세 조정 후 즉시 재비교 |
| **불편 포인트 *(가설)*** | 기존 툴은 사진 보정 중심이라 ISP 파이프라인 시각화 부재, 또는 ISP 툴은 UX가 낙후되어 있음 |

### 3.2 Secondary Persona — *이미지 신호처리 엔지니어*

알고리즘 단위 검증을 수행하며 파이프라인 블록(WB, Tone Curve, LUT 등)을 직접 작성/조정하는 엔지니어. Tuning 엔지니어보다 파라미터 수치에 더 민감하며 노드 그래프의 비선형 분기/합류를 자주 사용한다.

### 3.3 비대상 사용자 *(현 범위 밖)*
- 일반 소비자 사진가
- 비디오 콜로리스트
- 인증·권한 관리가 필요한 다중 사용자 팀 *(현재 단일 사용자 가정, 인증 미구현)*

## 4. Problem Statement

### 4.1 사용자 문제

**P1.** 엔지니어는 ref 이미지와 sim 이미지를 비교할 때 별도 뷰어를 띄우거나 파일 매니저를 오가며 비교한다 — 비교가 워크플로우의 1급 동작이 아니다.

**P2.** ISP 파이프라인의 어느 블록이 어떤 변화를 일으키는지 시각적으로 추적하기 어렵다 — 코드/설정 파일과 출력 이미지가 분리되어 있다.

**P3.** 색상 튜닝 파라미터(Tone Curve, HSL, Color Wheel, WB, LUT)를 조정하기 위해 매번 다른 도구를 켜야 한다.

**P4.** 작업 산출물(reference, simulation, 리비전, 메타데이터)이 폴더에 흩어져 있어 검색·태깅·버전 관리가 어렵다.

### 4.2 제품 가설

**H1.** ref ↔ sim 비교를 Split / Slider / Overlay 3가지 모드로 1급 기능화하면, 엔지니어는 별도 뷰어 없이 작업할 수 있다. *(→ FR-E2E-02)*

**H2.** 파이프라인을 Node graph + List + Timeline 3가지 시점으로 동시에 제공하면, 엔지니어는 자신의 사고 모델에 맞는 시점을 선택해 블록을 추적할 수 있다. *(→ FR-E2E-06, FR-E2E-07, FR-E2E-08)*

**H3.** 블록 선택 → 우측 패널에 해당 블록 전용 컨트롤이 즉시 뜨는 인터랙션이 컨텍스트 스위칭 비용을 줄인다. *(→ FR-E2E-09)*

**H4.** ref / sim 구분, 태그, 컬렉션, 즐겨찾기를 갖춘 Library가 있으면 산출물 관리 부담이 감소한다. *(→ FR-LIB-01 ~ FR-LIB-08)*

## 7. Key User Journeys

### 7.1 J1 — 새 튜닝 세션 시작

```
사용자가 앱 진입
  → Home 페이지 (지난 세션 / 진행 중인 작업 확인)
  → "Open E2E Pipeline" 카드 클릭 (또는 상단 [E2E] 탭)
  → E2E 페이지: 좌측 비교 뷰어(Split) + 하단 파이프라인(Node) + 우측 Tuning Panel(tone)
  → ref와 sim 차이를 Split 모드에서 확인
```

**참조**: FR-HOME-02, FR-SHELL-02, FR-SHELL-04, FR-E2E-01, FR-E2E-02

### 7.2 J2 — 파이프라인 블록을 시각적으로 추적

```
E2E 페이지에서 파이프라인 영역의 [List] 뷰로 전환
  → 단계별 처리 시간과 카테고리(source/correct/color/tone/output)를 한 줄씩 확인
  → 의심되는 블록 클릭 → 해당 블록이 선택 상태로 강조
  → [Node] 뷰로 다시 전환 → 동일 블록이 그래프 내에서 활성화
  → [Timeline] 뷰로 전환 → 그 블록이 차지한 시간 비중 확인
```

**참조**: FR-E2E-06, FR-E2E-07, FR-E2E-08 (3개 뷰가 동일한 선택 상태를 공유)

### 7.3 J3 — 색상 톤을 실시간으로 조정

```
E2E 페이지에서 파이프라인의 'tone' 블록 선택
  → 우측 Tuning Panel에 Tone Curve 인터랙티브 그래프 표시
  → 커브 컨트롤 포인트 드래그 → 즉각 시각 피드백
  → 동일 절차를 'hsl' / 'wb' / 'lut' / 'detail' 블록으로 반복
```

**참조**: FR-E2E-09 (블록 카테고리별로 다른 컨트롤 분기)

> ⚠️ 현재 한계: 커브 변경이 실제 sim 이미지에 반영되지 않음 — 시각 피드백은 컨트롤 자체에만 한정.

### 7.4 J4 — 산출물 정리

```
[Library] 탭 클릭
  → Collections 사이드바에서 'Night drives' 컬렉션 선택 → 필터링
  → 우측 메인에 해당 컬렉션의 그리드 표시
  → 검색창에 'iso 1600' 입력 → 메타데이터 일치 항목만 표시
  → 다중 선택으로 즐겨찾기 토글
  → [List] 뷰 전환 → 메타데이터(ISO, 일자, 세션) 표 형태로 확인
```

**참조**: FR-LIB-02, FR-LIB-05, FR-LIB-06, FR-LIB-07, FR-LIB-08

## 11. Risks & Open Questions

### 11.1 Risks

| ID | 위험 | 영향 | 완화 방안 |
|----|------|------|----------|
| **R1** | UI는 완성되었으나 실제 처리 엔진 부재 → 데모/구매 결정 시점에 실데이터 부재로 평가 어려움 | High | 최소한의 실 이미지 ↔ 파라미터 데모 경로 1개 우선 연결 |
| **R2** | Pipeline 뷰 3종 모두 유지하는 비용 vs. 실제 사용 분포 미검증 | Medium | 분석 도구 도입 후 6주 사용 데이터로 결정 |
| **R3** | `postMessage` target origin `*` (FR-SHELL-06, FR-TWK-06) — Claude Design 외 환경에서 잠재 보안 이슈 | Medium | origin allowlist 도입 |
| **R4** | localStorage 단일 키 (`whale:page`) 외에 작업 영속성 없음 → 새로고침 시 작업 손실 | High | 작업 상태(비교 모드, 선택 블록, 파이프라인 뷰 등) localStorage 또는 백엔드 영속화 |
| **R5** | DaVinci/Lightroom 사용자가 익숙한 단축키 부재 | Medium | 단축키 매핑 정의 → 구현 (Home의 ⌘E/⌘L 칩이 이미 시각적 약속) |

### 11.2 Open Questions

> requirements.md의 각 FR "평가 기준 없음" 항목에서 누적된 미해결 질문들:

**제품 정책:**
- Q1. 현재 단일 사용자 가정 — 다중 사용자 / 팀 협업이 향후 범위인가?
- Q2. 작업 결과(리비전) 저장은 로컬 / 클라우드 / 자체 호스팅 중 무엇인가?
- Q3. 실제 이미지 처리 엔진은 클라이언트 사이드 (WebGL/WASM) / 서버 사이드 / 외부 SDK 호출 중 어느 쪽인가?

**UX 정책:**

- Q5. Tweaks 패널을 일반 사용자에게 노출할지 (현재는 Claude Design 채널 한정) — 노출한다면 진입점은 어디인가 (Settings 버튼?)
- Q6. 단축키 정책 (현재 Home 카드에 칩만 표시, 핸들러 부재)

**디자인 정책:**
- Q7. 다크모드 추가 시점
- Q8. 모바일 / 태블릿 지원 여부 — 현재 의도적 제외이지만 영구 비대상인지 확인 필요

## 13. Glossary

| 용어 | 정의 |
|------|------|
| **ref / Reference** | 센서/렌즈에서 캡처된 원본 이미지 (튜닝의 목표 또는 비교 기준) |
| **sim / Simulation** | 파이프라인을 거쳐 출력된 이미지 (조정 대상) |
| **Pipeline / 파이프라인** | 이미지 처리 블록의 순차/네트워크 구성 (예: source → WB → tone → HSL → output) |
| **Block** | 파이프라인을 구성하는 단위 처리 단계 (카테고리: source / correct / color / detail / tone / output / sink) |
| **Pass / Revision** | 파이프라인 한 번의 실행 결과 단위 (`pass-3 · rev-7`) |
| **Compare Viewer** | E2E 페이지의 ref ↔ sim 비교 영역 (Split / Slider / Overlay 3가지 모드) |
| **Tuning Panel** | E2E 페이지 우측 320px 고정 폭 패널 — 선택된 블록의 파라미터 컨트롤 |
| **Tweaks** | Accent / Density 등 디자인 토큰 변경용 우하단 플로팅 패널 (Claude Design 호스트 한정) |
| **Edit-mode** | Claude Design 호스트가 iframe 내부 앱과 통신하기 위한 `postMessage` 프로토콜 |
